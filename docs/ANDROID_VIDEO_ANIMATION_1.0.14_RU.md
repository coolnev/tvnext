# TVNext 1.0.14: облегчение анимации видео

Пользователь сообщил: после устранения вспышки списка каналов сворачивание видео выглядит медленным и тяжёлым. Исправление должно сохранить защиту от вспышек, просмотр 4K и единственную видеоповерхность.

## Подтверждённая лишняя работа

В SharedVideoStage значение Animatable<Rect> читалось прямо во время композиции. Размеры этой рамки передавались в requiredSize самого окна и NativePlayerSurface. Поэтому каждый промежуточный кадр заново вызывал композицию дочернего видео, измерение и изменение его размера.

Воспроизводимая проверка на восьми виртуальных кадрах дала **8 композиций, 8 измерений и 8 изменений размера** видео. Это счётчики модели Compose с подставным видеоэлементом, а не замер физического GPU или FPS телевизора.

## Изменение

- Во время перелёта размеры нативного окна остаются равны последней завершённой раскладке. Перемещение и масштаб читают анимированную рамку только внутри graphicsLayer; Composition и Layout не подписаны на каждый кадр.
- В конце назначение получает свою обычную раскладку и обрезку. Статический просмотр и выключенная анимация сохраняют прежние размеры.
- Вместо отдельного слоя для альфы и clipToBounds используется один графический слой с прямоугольной обрезкой и началом преобразования в левом верхнем углу.
- Переход длится **300 мс вместо 420 мс**.
- При отмене/развороте активного перехода сохраняется прежняя нативная раскладка; следующий перелёт начинается с текущего отображаемого положения. Проверен быстрый возврат во время расширения.

Навигационная защита 1.0.12 остаётся: прежнее видео находится над новым интерфейсом до измерения назначения, включая задержанное подключение окна. Плеер и поверхность не пересоздаются при переходе. SurfaceView и его Compose sync workaround сохранены. Изменений в настройках, Amlogic-декодере, Dolby, EPG и AFR нет.

## Результат проверки

На тех же восьми виртуальных кадрах после исправления: **0 композиций, 0 измерений, 0 изменений размера** дочернего видео. Отображаемые границы продолжают двигаться между кадрами, затем совпадают с назначением. Проверяются прерывание движения, окончания переходов, одна поверхность, закрытие списков/переход на главный экран, отсутствие преждевременного показа нового интерфейса и обрезанный preview.

Фактическая плавность и синхронизация SurfaceView/SurfaceFlinger на Ugoos/TCL здесь не измерены. Android API 28/35 проверяет тип и сохранение нативной поверхности; Compose-кадры и счётчики подтверждают устранение лишней работы в общем UI. APK на физическом телевизоре не запускался.

## Первичные источники

- [Google: оптимизация анимации Compose](https://developer.android.com/develop/ui/compose/animation/quick-guide#optimize-animation-performance): отложенное чтение анимированного состояния в graphicsLayer исключает Composition/Layout из покадровой работы.
- [Google: графические преобразования](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers): scale/translation и выбор начала преобразования работают на уровне графического слоя.
- [Google Media3: типы поверхностей](https://developer.android.com/media/media3/ui/surface): SurfaceView предпочтителен для Android TV/полного разрешения; синхронизация анимации поддерживается с API 24. Для PlayerView внутри AndroidView есть ограничения совместимости, поэтому универсальная гарантия поведения на всех прошивках без запуска на устройстве невозможна.
